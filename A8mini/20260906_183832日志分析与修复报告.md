## 4. 软件问题为何会把故障拖长

核对的外部采集源码是 `/home/q/Documents/A8mini_Detction/rtsp_capture.py`，仓库 HEAD `c83acee62033aae86ef89380ba180f7c29e07fa2`。历史日志没有保存此未跟踪文件的源码快照，因而源码对应关系以现有文件和日志行为相互印证，不宣称历史文件哈希已核实。

1. `capture_worker()` 只在 `ok=False` 或帧为空时重连，成功返回则无条件发布。日志中 CAP=2515.7 ms 的帧明确走进了推理，说明一次 OpenCV 超时警告不等于 Python 一定收到失败。
2. `captured_at` 设置在 read 返回之后，随后 AGE 只计算共享帧等待和推理时间。因此 AGE=67.8 ms 不包含此前 2515.7 ms 的阻塞，更不包含相机编码/网络内部缓存。这个指标不能当作端到端实时延迟。
3. watchdog 对每次新的 read 阶段都重新计时，没有独立的“多久没收到合格帧”预算，缓慢成功帧能不断续期。
4. `streaming` 在曾收到帧后一直保留，直到重连才改变。等待页因此出现相互矛盾的 `Waiting: streaming`。

OpenCV 官方实现将网络中断回调和帧抓取/解码分开处理；应用必须自己判断最终返回是否符合实时要求，不能只观察告警文本。[OpenCV FFmpeg 后端源码](https://github.com/opencv/opencv/blob/4.x/modules/videoio/src/cap_ffmpeg_impl.hpp)。此在线源码用于理解实现，不作为当时二进制版本一致性的证明。

## 5. 哪些原因有证据，哪些没有

- **已证实**：视频接收/解码异常、HEVC 参考帧缺失、部分时段 UDP 也响应超时、旧代码接受超时返回帧。HEVC 错误说明解码所需参考状态不完整；不能仅据此定位到某根网线丢包，重连从 GOP 中间加入也可能产生这类错误。
- **尚不能确定**：相机内部编码/服务异常、以太网接触或交换路径、供电波动、主机资源争用各占多少。两次扫描附近出现异常具有相关性，但最后一次故障在扫描完成约 40 秒后出现，不应只改云台扫描角度并宣称解决。
- **不支持的解释**：本次由识别视频写盘引发；YOLO 持续推理数秒导致黑屏；ROS 1 到期弹窗直接导致 RTSP 超时。截图的 ROS 弹窗只是版本维护提醒；右侧约 171 Hz 属于另一个话题，不能当作视频帧率。雷达 `Handle detection data` 也不是 YOLO 检测结果。
- **飞控数据仍在运行**：按 rosbag 接收时间统计，18:41:43–59、18:42:02–15、18:42:58–18:43:20 三个窗口内，EKF/IMU 均约 171.2 Hz，姿态指令约 200.0/200.0/199.9 Hz，LIO 约 10.0 Hz。EKF 最大相邻接收间隔分别 19.0/14.3/26.6 ms，姿态指令 15.1/13.0/24.9 ms。这排除了这些窗口内的整套 ROS 同步停摆，不能据此推导 CPU/GPU 有充足余量或绝对没有调度抖动。

当前配置下，一次 read 耗时达到约 2.5 s 即认定失败；若原生调用不返回，或反复返回超过帧有效期的帧，独立 watchdog 在最后合格帧/首个 read 后约 **2.75 s** 开始清理连接（2.5 s + 250 ms 宽限，实际受调度影响）。不会再由“超时后成功返回”的帧将这一故障拖成四轮约 2.5 s 等待。

**2.75 s 是检测/触发预算，不是恢复出图保证。** 之后还有进程终止、1 s 重连间隔、spawn/import、RTSP 打开和等待可解码帧。相机持续掉线或持续输出损坏视频时仍会显示等待、继续重试；单纯快速重连也无法恢复不存在的参考帧。这次没有启用硬解码、改相机编码或增加 CPU/GPU 限额，避免把未验证的资源假设混进修复。

## 8. 若还有物理断流，下一步怎么定位

按现有证据优先做同一配置的地面对照，而不是继续盲目加大读取超时：

1. **比对相机公共路径。** 对齐新的 RTSP 时标和云台独立日志；如果 RTSP 和 UDP 再次同时中断，检查相机供电、接头、以太网路径，并对比静止与扫描时是否更易出现。日志相关性不能替代供电实测。
2. **保留链路证据。** 复测前后记录 `ip -s link` 的错误/丢弃计数；复测中另开终端运行 `ping -D -i 1 192.168.144.25` 留存时间和响应。ping 正常只能说明 ICMP 当时可达，不能保证 RTSP 数据或解码正常。需要进一步定责时再抓相机 RTSP TCP 流，区分服务器停发、重传及客户端解码问题。
3. **补主机负载。** 复测时保存 Jetson `tegrastats --interval 1000` 输出并记录开始时间；当前 `cpu_threads: 2` 控制部分计算库，不是全机资源上限，也未显式限制 FFmpeg 解码线程。只有负载证据支持时，再对比关闭识别或降低推理上限后的结果；降低 `max_fps` 不会降低相机推流码率。
4. **单独验证 HEVC 恢复。** 如果网络和 UDP 都正常但持续缺参考帧，记录相机实际编码、码率、帧率和关键帧间隔，再用同一条流作解码对照。不能通过修改 URL 后缀或只把 YAML 的 codec 改成 h264 来改变相机实际编码。硬解码作为后续性能方案，必须先确认目标 Python 的 OpenCV 和 Jetson 解码插件可用；当前环境直接设 gstreamer 会引入新的打不开流问题。

这些对照的目标是消除触发源；本次软件修复负责及时拒收异常帧并恢复连接。两者需要分别验收。
