## 1. 详细分析

### 问题 1 — RViz 3D 黑屏（固定系 world 缺 TF）

**现象**：RViz 右上 `Global Status` 红色报错 `Fixed Frame [world] does not exist`，3D 区全黑（连 Grid 都不画）。

**链路**：
`sh_files/one_click_takeoff.sh` → `run_single_lio.sh` → `start_launch diff_planner exp_rviz.launch`
→ [exp_rviz.launch](../src/diff_planner/plan_manage/launch/exp/exp_rviz.launch) 加载 [exp.rviz](../src/diff_planner/plan_manage/launch/include/exp.rviz)，其中 `Fixed Frame: world`（第 6066 行）。

**根因**：
- 真机 TF 里**没有任何节点发布 `world`**。唯一的世界系来自 faster-lio，其世界系名默认是 `camera_init`：
  - [laser_mapping.cc](../src/realflight_modules/faster-lio/src/laser_mapping.cc#L788) 广播 `camera_init` → `body`；
  - 参数默认值 `publish/tf_world_frame = "camera_init"`（[laser_mapping.cc](../src/realflight_modules/faster-lio/src/laser_mapping.cc#L68)）。
- EKF（[ekf_node_vio_timesync_with_acc_pub.cpp](../src/realflight_modules/ekf_pose/src/ekf_node_vio_timesync_with_acc_pub.cpp#L117)）只把 `/ekf/ekf_odom` 的 header 标成 `world`，**并不广播 TF**（`ekf_pose` 源码里没有任何 `sendTransform`/`TransformBroadcaster`）。
- 真正会广播 `world` 的 `odom_visualization` 只在仿真里启动（[simulator.xml](../src/diff_planner/plan_manage/launch/include/simulator.xml#L52)），真机 launch 不含。
- 日志佐证：`flight_logs/20260929_151437/flight_debug.bag` 里 `world` 出现 24988 次，正好等于 `/ekf/ekf_odom` 条数（24988），而 `/tf` 条数（1593）≈ `/laserMapping/odometry` 条数（1596）→ **`/tf` 只有 `camera_init`→`body`**。

**已做修复**：在 [mid360.yaml](../src/realflight_modules/faster-lio/config/mid360.yaml#L49) 的 `publish:` 下新增
```yaml
    tf_world_frame: world # match the world frame used by EKF / planner / RViz
```
`run_mapping_online` 通过 ROS 参数加载该 yaml，改这里生效。效果：faster-lio 的 TF / odom / 点云世界系统一为 `world`，与 EKF、planner（`grid_map/frame_id=world`）、RViz 一致。

**验证**：第二次运行（`20260929_155840`）RViz `Global Status` 变为 **Fixed Frame OK**，Grid 正常显示。

> 备选方案（若不想改 LIO）：在真机 launch 里加
> `<node pkg="tf2_ros" type="static_transform_publisher" name="world_to_camera_init" args="0 0 0 0 0 0 world camera_init"/>`。

### 问题 2 — RViz 底部 Image 面板 "No Image"

**现象**：RViz 左下角 `Image` 面板显示大字 `No Image`。

**根因**：当时 `exp.rviz` 根层的 Image display 订阅 `/camera/color/image_raw`，而真机检测进程没有发布该话题。配置里还有一个默认关闭的仿真图像显示 `/drone_0_pcl_render_node/colordepth`；它不是截图左下角这个启用的根图像显示。2026-09-30 已移除无数据的根图像显示，并加入 `/laserMapping/cloud_registered` 实机点云。

**结论**：这不是相机故障，而是 `exp.rviz` 复用仿真配置留下的死面板。**A8mini 的实时画面本来就不经过 RViz**：检测进程是独立程序，画面显示在它自己的 OpenCV 窗口（标题 `A8 mini realtime detection`）。

**处理建议**（按需）：
- 想在 RViz 里看相机时，需要先有节点实际发布图像话题，再按该话题配置 Image 显示；
- 现在就想看相机画面，可先脱离检测直接用 ffmpeg 播放（相机流已确认可用）：
  ```bash
  ffplay -rtsp_transport tcp rtsp://192.168.144.25:8554/main.264
  ```
  （实测该 RTSP 流：`hevc`(H.265)，1920×1080，可正常拉流。）

### 问题 3 — A8mini 识别不弹窗

识别节点是独立子进程（`a8mini_detection_node.py` 监管 `a8mini_detection.py`），任一步失败即秒退，没有窗口。两次运行分别命中两个不同错误。

#### 3a（第 1 次，`20260929_151437`）— 当时配置的仓库路径无效
```
[DETECTION_PROCESS] ... [ERROR] Detection failed:
FileNotFoundError: A8mini_Detction repo_path is invalid: /home/ly/Documents/A8mini_Detction
[ERROR] A8 mini detection exited with code 1; check detector output
```
- 配置 [a8mini_detection.yaml](../src/user_command/multipoint/config/a8mini_detection.yaml#L4) 里 `repo_path: ~/Documents/A8mini_Detction`，但该外部仓库当时整机不存在。
- **当时的临时恢复**：用户把外部仓库传回后，路径问题暂时消失。**后续已改为单仓部署**：项目内现在包含 `yolo11s.engine`、`yolo11s.names.json` 和标签绘制代码，配置、检测入口、诊断和测试都移除了 `repo_path`；不再需要复制或保留外部仓库。详见[整合说明](../A8mini/20260930_A8mini检测单仓整合说明.md)。

#### 3b（第 2 次，`20260929_155840`）— Python 环境缺 torch
```
[DETECTION_PROCESS] ... [ERROR] Detection failed: ModuleNotFoundError: No module named 'torch'
[ERROR] A8 mini detection exited with code 1; check detector output
```
- **根因**：检测依赖（torch / ultralytics / opencv 等）原本装在**旧用户**的 user site-packages。
  证据见旧机运行时快照 `flight_logs/20260917_174111/detector_runtime_11008/manifest.json`：
  ```json
  "python_executable": "/usr/bin/python3",
  "packages": {
      "ultralytics": "8.4.89",
      "torch": "2.1.0a0+41361538.nv23.6",
      "numpy": "1.23.5",
      "tensorrt": "8.5.2.2",
      "opencv-python": "5.0.0.93"
  }
  ```
  且日志里 cv2 路径为 `/home/q/.local/lib/python3.8/site-packages/cv2/...` → 说明这些包装在**旧用户 `~/.local`**。
- **现状**（本机 `ly`）：
  - `find / -name torch`（site-packages）无结果；`/home/ly/.local/...` 为空；`/home/q` 已不存在。
  - `/usr/bin/python3 -c "import torch"` → `ModuleNotFoundError`；
  - 现有：`numpy 1.17.4`、`tensorrt 8.5.2.2`、`cv2 4.2.0`；缺 `torch`、`ultralytics`。
- **待修**：重装检测 Python 环境（见 §3 待办）。

### 问题 5 — 规划节点 `drone_0_diff_planner_node` 挂 exit 127

**现象**（`20260929_155840/key_events.log`）：
```
[drone_0_diff_planner_node-1] process has died [pid 31092, exit code 127, cmd .../diff_planner_node ...]
```
手动运行证实：
```
diff_planner_node: error while loading shared libraries: libtraj_opt.so: cannot open shared object file
```
（这是未 `source` 环境时的表现）；`source devel/setup.bash` 后 `libtraj_opt.so`/`libplan_env.so` 能找到，但仍有：
```
libopencv_core.so.406 => not found
libopencv_imgcodecs.so.406 => not found
```
**根因**：
- 本机 OpenCV 只有 **4.2** 与 **4.5**（`/usr/lib/aarch64-linux-gnu/`、`ldconfig`），**没有 4.6**。
- 而 `diff_planner_node` 是在 **OpenCV 4.6.0（安装在 `/usr/local`）** 下编译的：
  `build/diff_planner/CMakeCache.txt` → `OpenCV_DIR=/usr/local/lib/cmake/opencv4`，`FIND_PACKAGE_MESSAGE_DETAILS_OpenCV=[/usr/local][v4.6.0()]`。
- 即：迁移后 `/usr/local` 里的 OpenCV 4.6 丢了，二进制按 `libopencv_*.so.406` 找库失败 → 加载即退出（127）。

**影响范围**：全 `devel/lib` 扫描，仅以下两个二进制缺 `libopencv_*.so.406`：
- `devel/lib/diff_planner/diff_planner_node`（**真机必用**，负责规划）
- `devel/lib/drone_detect/drone_detect`（真机链路未用）

**运行佐证**：`rosnode_list.txt`（`151437`/`155840`/`145528`）都没有 `drone_0_diff_planner_node` → 该节点一直是挂的，因此 RViz 里看不到规划轨迹/地图，任务也无法自主规划。

**待修**（三选一，见 §3）：
1. 重新安装 OpenCV 4.6 到 `/usr/local`（源码编译，耗时）；
2. 用系统 OpenCV（4.2/4.5）**重新编译** `diff_planner`（`catkin_make --pkg diff_planner`，注意与系统 cv_bridge 一致）；
3. 临时符号链接 `libopencv_*.so.406 → 系统 4.5 库`（ABI 未必完全兼容，仅应急，需回归验证）。

## 2. 根因归并：一次迁移带来的连锁问题

工作空间从旧机旧用户 `/home/q/Documents/diff-planner-A8mini*` 整体拷到 `/home/ly/Documents/diff-planner-A8miniV2`（详见 [repo memory: workspace-relocation]）。这次迁移丢了两类**运行环境**（不是源码）：

1. 用户级 Python 包：旧 `~/.local/lib/python3.8/site-packages` 里的 `torch / torchvision / ultralytics / opencv-python / numpy(1.23.5)` → **检测失效**（问题 3b）。
2. 系统级 `/usr/local` 下的 OpenCV 4.6 → **规划节点失效**（问题 5）。

另外两类是**文本里写死的旧路径**：
3. catkin 生成的 python 中继 `devel/lib/**/<script>.py` 写死 `/home/q/...` → **云台节点失效**（问题 4，已修）。
4. 其余 `devel` 里约数百个 `*.cmake/*.pc/*.fish` 仍指向旧路径（一般不影响运行，但重新编译前建议清理）。

而 RViz 黑屏（问题 1）属于**代码/配置层面的固有缺陷**（仿真配置 `exp.rviz` 的 `world` 在真机 TF 中无人发布），与迁移无关，但同样暴露了真机链路缺少 `world` 帧。

## 3. 当时的待办 / 修复清单（历史记录）

以下是 9 月 29 日的备选方案。当前本机已经用工作空间内的检测环境和完整重编译处理这两个故障；不要按旧清单给系统库做 `.406` 软链接，也无需覆盖 ROS 使用的系统 Python 包。当前操作和验证边界见[单仓整合说明](../A8mini/20260930_A8mini检测单仓整合说明.md)。

### A. 重装检测 Python 环境（对应问题 3b）
目标：让 `/usr/bin/python3` 用户级可 `import torch, ultralytics, cv2, numpy`（且版本匹配 Jetson / TensorRT）。
建议复刻旧机可用版本：
- torch = `2.1.0a0+41361538.nv23.06`（JetPack 5.1.x 的 NVIDIA 构建；实测下载索引可用）
  ```bash
  /usr/bin/python3 -m pip install --user --no-cache-dir \
  "https://developer.download.nvidia.com/compute/redist/jp/v512/pytorch/torch-2.1.0a0+41361538.nv23.06-cp38-cp38-linux_aarch64.whl"
  ```
- torchvision：需与该 torch 匹配（NVIDIA 的 Jetson torchvision 通常需按官方 “PyTorch for Jetson” 步骤源码编译，或找对应 wheel）。
- ultralytics：`/usr/bin/python3 -m pip install --user "ultralytics==8.4.89"`（装前先确保 torch 已在，避免 pip 去拉 x86 轮子）。
- numpy：ultralytics 需 `>=1.23`，本机系统是 1.17.4 → 用 `--user` 装 `numpy==1.23.5` 覆盖（注意别动到 ROS 依赖的 numpy，风险点见下）。
- opencv-python：ultralytics 需 `>=4.6`，本机 cv2 是 4.2.0 → `--user` 装 `opencv-python`（旧机为 5.0.0.93）。

> 风险与注意：
> - ROS noetic 的 Python 与 `/usr/bin/python3` 是同一个解释器，`--user` 覆盖 numpy 可能影响 ROS 节点。旧机正是这样用的（numpy 1.23.5 在 `~/.local`），可参考。
> - 装完先在**独立终端**验证，不要一边飞一边装：
>   `/usr/bin/python3 -c "import torch, ultralytics, cv2, numpy; print(torch.__version__, numpy.__version__, cv2.__version__)"`
> - TensorRT 8.5.2.2 已在系统内，但版本相同不足以保证旧 `.engine` 的最佳性能。
>   2026-10-03 同一 engine 在本机能运行，并出现设备参数差异警告；同为 Orin NX 时，
>   内存规格、功耗模式及活动 GPU SM 数也需核对。优先消除整机 CPU 争用；固定最终
>   功耗模式后可在本机重导作对照，见 [10 月 3 日视频卡顿分析](20261003_170857_A8mini视频卡顿分析.md)。
