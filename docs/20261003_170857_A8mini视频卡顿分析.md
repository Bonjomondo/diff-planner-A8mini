## 结论与证据范围

这次最明确的问题是完整栈运行时整机 CPU 持续满载；当前 15W 模式只开放 4 个 CPU 核，
检测使用 FFmpeg 软件解码 1080p H.265，并以 nice +10 运行。模型加载、预热、视频解码、
识别和桌面显示一起争用资源。历史超时重连修复仍然有效，并未在 9 月 30 日整合中丢失。

旧 `.engine` 在本机确实出现设备参数差异警告，但能够执行。同一模型在停止飞行栈后
明显恢复速度，不能把约 2 FPS 全部归因于外机导出的 engine，也不能承诺仅重导即可恢复。

依据：最新日志 `flight_logs/20261003_170857`、提交历史、本机只读功耗/插件检查，
以及停止飞行栈后的离线推理和合成视频硬解验证。没有启动飞控或发送相机控制命令。
本次真实相机 RTSP 打开未成功，因此新增硬解通路尚未完成真实云台/完整栈复测。

### 为什么出画面慢

- 17:09:40.345：ROS 监督器报告检测子进程开始。
- 17:10:25.023：检测程序进入模型预热；此前启动/导入阶段约 44.7 秒。
- 17:11:14.921：预热完成后才开始采集；预热阶段约 49.9 秒。
- 17:11:16.331：FFmpeg 采集子进程连接。
- 17:11:19.748：第一帧；本次 RTSP 连接约 3.4 秒，距检测子进程启动约 99.4 秒。

所以这段启动时间主要花在导入推理环境和预热，不能把近 100 秒全算成 RTSP 连接慢。
现有检测设计先预热再打开视频；本次增加这两段耗时的明确日志，便于下次直接比较。

### 为什么会断一下

17:11:45.587 已执行历史修复：一次 `read()` 虽返回 `ok=True`，耗时 **2635.3 ms**
仍被拒收并重连。17:11:50.838 恢复首帧，距上次合格帧约 **7.86 秒**。
其中包含故障发现、旧进程清理、1 秒重连间隔、spawn 与重新等待可解码帧。

TCP 快照中，17:11:25 接收队列已积压 **1,060,893 字节**；随后降到 902,660、567,620、
99,946 字节，而累计接收字节主要停在约 2.3 MB，仅少量增长。它支持客户端消费不及时、
存在上游积压的判断；也不能排除相机 RTSP 服务在该连接上停流。
ping 正常只能说明基本 IP 连通，不能证明 RTSP 视频持续正常。

## 功耗模式与是否重导 `.engine`

已经找到原始权重：`/home/ly/Documents/A8mini_Detction/yolo11s.pt`。
类别名称与当前 `yolo11s.names.json` 的 80 类逐项一致；同目录也有旧 engine。
旧 plan 无标准 Ultralytics JSON 元数据头，类别表相同本身不能证明所有权重完全相同。

本机为 Orin NX 16 GB、CUDA 11.4、TensorRT 8.5.2.2，当前 CUDA 看到 **4 个 SM**。
`/etc/nvpmodel.conf` 中 15W 的 GPU TPC 掩码为 252，25W/MAXN 为 240。
NVIDIA [engine 兼容性文档](https://docs.nvidia.com/deeplearning/tensorrt/latest/inference-library/engine-compatibility.html)
说明 SM 数等设备属性差异也会触发警告。因此，两台均为 Orin NX 时，当前警告也可能与
功耗模式或模块规格差异有关；未拿到旧机运行模式，无法确认具体是哪一项。

建议先启用硬解并固定最终部署功耗模式，再决定是否重导。供电和散热适合 25W 时，
本机配置中 **25W 是 mode 3**，并非其他 Jetson 教程里可能使用的 mode 0：

```bash
sudo nvpmodel -m 3
nvpmodel -q
cat /sys/devices/system/cpu/online
```

25W 配置开放 8 个 CPU 核，也开放更多 GPU 单元。若模式切换提示需要重启，按提示重启后
再测试；本次没有切换系统模式。保持同一模式比较启动、FPS、AGE、重连数和飞行相关频率。
同时可用降低 NoMachine 分辨率/刷新率或本地显示器作对照，确认桌面负载的影响。

**重导建议：** 同型号 NX 且运行时匹配，不是仅因换了一台就必须重导；现有 engine
已经通过本机推理验证。为了与最终模式匹配并排除跨环境策略差异，建议之后在本机导出
一个 FP16/640/batch 1 候选，与旧 engine 比较后再切换，保留旧文件作为回退。

当前环境尚未装 ONNX。以下是候选导出的操作示例，本次未执行导出、未替换现有 engine。
ONNX 1.16.2 提供 Python 3.8/aarch64 包，见 [官方发布包](https://pypi.org/project/onnx/1.16.2/)。
使用当前 Ultralytics 8.4.159 的 `quantize=16` 参数；关闭 simplify 避免额外安装
onnxruntime/onnxslim。先停止飞行栈，在最终选定功耗模式下执行：

```bash
cd /home/ly/Documents/diff-planner-A8miniV2
.venv-a8mini/bin/python -m pip install --only-binary=:all: 'onnx==1.16.2'
ULTRALYTICS_AUTOINSTALL=False .venv-a8mini/bin/python - <<'PY'
from datetime import datetime
from pathlib import Path
import json
import os
import shutil

for key in ('OMP_NUM_THREADS', 'OPENBLAS_NUM_THREADS', 'MKL_NUM_THREADS'):
    os.environ[key] = '2'
from ultralytics import YOLO

# 复制到新的目录导出，避免覆盖原目录及在用的 engine。
folder = Path('.venv-a8mini/engine_candidates') / datetime.now().strftime('%Y%m%d_%H%M%S')
folder.mkdir(parents=True, exist_ok=False)
weights = folder / 'yolo11s.pt'
shutil.copy2('../A8mini_Detction/yolo11s.pt', weights)
model = YOLO(str(weights), task='detect')
names = {str(k): v for k, v in model.names.items()}
weights.with_suffix('.names.json').write_text(json.dumps({'names': names}, indent=2) + '\n')
engine = model.export(format='engine', imgsz=640, batch=1, device=0,
                      quantize=16, dynamic=False, simplify=False, opset=12, workspace=2)
print('Candidate engine:', engine)
PY
```

这是待实测的导出参数，并非已完成的导出验收。导出后先通过检测入口的 `--model`
或 launch 的 `model:=绝对路径` 对候选作独立比较，核对真实画面类别和置信度；然后使用
完整栈复测。不能只凭成功导出或警告消失，就认定视频问题已经解决。
